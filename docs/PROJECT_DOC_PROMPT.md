# 项目文档生成 Prompt

> 这是一份**可复用的项目文档生成提示词**。换一个项目，改掉「变量区」里的占位符就能直接用。
>
> 本文件的价值不在于「把文档写得好看」，而在于**把「凭印象写文档」变成「按可执行的核查清单写文档」**。
> 下面 Prompt 的每一条约束都对应一种真实的文档事故 —— 它们是踩过的坑，不是模板套话。

---

## 一、变量区（使用时替换）

把下面的 `{{...}}` 换成目标项目的真实值。**填不出来的项写「待确认」，不要编**。

| 变量 | 说明 | 本项目实例 |
|---|---|---|
| `{{PROJECT_NAME}}` | 项目名 | 学生管理系统 |
| `{{PROJECT_ROOT}}` | 项目根目录绝对路径 | `<项目根目录>` |
| `{{DOC_TARGET}}` | 文档输出路径 | `docs/ARCHITECTURE.md` |
| `{{SCOPE}}` | 覆盖范围 | 全栈三端：FastAPI 后端 + Vue3 前端 + KB 小助手 |
| `{{AUDIENCE}}` | 读者 | 接手的新同事 / 半年后忘事的自己 |
| `{{STACK}}` | 技术栈 | FastAPI + SQLAlchemy 2.0 + MySQL + Vue3 + TS + Vite |
| `{{ENTRYPOINTS}}` | 启动命令 | `python main.py` / `npm run dev` / `kb_assistant/start.ps1` |
| `{{VERIFY_CMDS}}` | 验证命令 | `pytest tests/` / `npm run verify` |

## 二、Prompt 正文（直接复制使用）

```text
你是资深技术文档工程师。请为下面的项目撰写一份**面向接手者**的技术文档。

════════════════════════════════════════════════════════════
【一、项目坐标】
════════════════════════════════════════════════════════════
项目名称：{{PROJECT_NAME}}
项目根目录：{{PROJECT_ROOT}}
文档输出到：{{DOC_TARGET}}
覆盖范围：{{SCOPE}}
目标读者：{{AUDIENCE}}
技术栈：{{STACK}}

════════════════════════════════════════════════════════════
【二、最高原则：文档里的每一条事实都必须可验证】
════════════════════════════════════════════════════════════
这是本任务的**第一优先级**，高于文采、结构、篇幅。

1. **不许凭印象写。** 每一个接口数量、端口号、表名、字段名、文件路径、
   行号、测试数量，都必须来自你实际读过的代码或实际跑出来的结果。
   宁可写「未验证」，也不要写一个看起来很合理的数字。

2. **能跑就跑。** 凡是声称「测试通过」「接口可用」的地方，
   你必须**实际执行**对应命令并贴出真实输出摘要。
   没跑过的，一律写成「未验证」，而不是「应该没问题」。

3. **数量类结论用工具产出，不要用眼睛数。**
   - 接口总数 → 从应用对象导出 OpenAPI 后统计 operation 数，不要手数路由装饰器
   - 测试数量 → 用测试框架的收集结果统计
   - 表行数   → 直接查库，不要相信文档里写的
   - 目录结构 → 用文件遍历命令生成，不要凭记忆罗列

4. **发现文档与代码不一致时，如实记录，不要替代码圆场。**
   在「已知问题」章节单列一张表：位置 / 文档写的 / 实际是什么 / 影响。
   如果你顺手把代码改对了，也要在表里标注「已修」并说明改了什么。

5. **发现真实缺陷时，写清三件事**：根因（具体到文件与行号）、
   触发条件、以及最坏后果。
   特别注意「静默失败」类缺陷 —— 写错库但接口返回 200、
   数据提交了但响应 500 —— 这类问题比崩溃更危险，必须单独标注。

════════════════════════════════════════════════════════════
【三、必做的核查动作（按顺序）】
════════════════════════════════════════════════════════════
动手写文档之前，先完成这些核查。核查结果直接进文档。

□ 1. 遍历项目目录，生成真实的目录树（含文件大小），识别各子系统的边界
□ 2. 找出所有可执行入口（main / app 工厂 / package.json scripts / 启动脚本）
□ 3. 导出后端全部路由清单：方法 + 完整路径 + 归属模块 + 数量统计
     与项目里任何现存的接口清单文档逐条比对，找出差异
□ 4. 跑后端测试套件，记录通过/失败/报错的**真实**数字，
     并对失败项逐个定位根因（是代码缺陷、测试过期、还是环境问题）
□ 5. 跑前端类型检查与构建、接口契约体检脚本，记录真实结果
□ 6. 连接数据库，统计各表真实行数，与种子数据基线比对，
     识别并清理调试残留（清理前先记录，避免破坏他人数据）
□ 7. 核对环境变量：代码里实际读了哪些、默认值是什么、文档写的对不对
□ 8. 通读既有 README 与调试笔记，提取「踩过的坑」——
     这些是文档里最有价值、最难重新发现的内容，绝不能丢

════════════════════════════════════════════════════════════
【四、文档结构（按此组织，章节可增不可减）】
════════════════════════════════════════════════════════════
一、项目概述          —— 是什么、解决什么问题、核心功能表、技术选型（含「为什么选它」）
二、整体架构          —— 拓扑图、服务清单（端口/启动方式/权限）、目录结构
三、后端分层设计      —— 分层职责边界、调用链、每层的关键约定与踩坑点
四、数据库设计        —— 表清单、关系图、字段约定、ORM 与 SQL 脚本的一致性风险
五、接口清单          —— 按模块分组的方法+路径+说明表 + 响应格式差异 + 状态码语义
六、从零跑起来        —— 环境要求、前置依赖、分步命令、常见启动失败
七、测试              —— 两套测试的分工与跑法、当前真实状态
八、前端              —— 技术栈、关键设计（适配层等）、验证方式
九、知识库/旁路服务   —— 定位、边界、安全设计、配置
十、已知问题          —— 遗留缺陷 + 架构待改进项 + 文档不一致表
附录：配套文档索引    —— 与本项目其他文档的关系图

════════════════════════════════════════════════════════════
【五、写作规范】
════════════════════════════════════════════════════════════
- **语言**：中文。术语、字段名、路径、命令保持原样不翻译。
- **风格**：讲「为什么这样设计」和「这里踩过什么坑」，
  而不只是罗列「有什么」。文档的价值在于让读者少踩一遍。
- **具体**：给出可复制的命令、真实的代码片段、可对照的表格。
  避免「需要注意」「建议使用」这类没有信息量的表述。
- **诚实**：做不到的、没验证的、依赖外部条件的，明确标注。
  宁可承认边界，也不要制造虚假的完整性。
- **标注时间**：结尾写明「本文基于 <日期> 的代码状态编写」。
- **安全**：不要在文档里写入真实的密码、token、密钥。
  写「见 .env 的 DB_PASSWORD」并提醒 .env 已被 gitignore 排除。

════════════════════════════════════════════════════════════
【六、交付前自检】
════════════════════════════════════════════════════════════
□ 文档里每个数字都能指到它的来源（代码位置或命令输出）
□ 所有启动命令都是实际可行的，端口与配置与代码一致
□ 所有「已知问题」都有具体文件行号，不是泛泛而谈
□ 没有泄露任何真实凭证
□ 与项目现有文档互相索引，不重复也不矛盾
□ 读者照着「从零跑起来」能真的跑起来
```

## 三、为什么这样写

这份 Prompt 的设计不是「让文档更详细」，而是**堵住三个具体的失效模式**。

### 失效模式一：数字靠数

写「本项目共 51 个接口」时，人会数路由装饰器，或直接抄现有文档里的数字。
但文档写着 51、代码实际 48 条路径 51 个 operation，或者文档写 50、实际 51 —— 
这种偏差会直接让读者怀疑整份文档。

**对策**：Prompt 明确要求「数量类结论用工具产出」，并给出具体手段
（从 OpenAPI 导出、用测试收集器统计、直接查库）。

### 失效模式二：把「应该是这样」写成「是这样」

文档里写「测试全部通过」，实际跑一遍有 7 失败 31 报错 —— 
读者一跑就发现对不上，整份文档的可信度归零。

**对策**：要求「没跑过的一律写未验证」，并把「实际执行并贴出输出摘要」
列为高于文采的硬约束。

### 失效模式三：漏掉静默失败

崩掉的代码会告诉你它坏了。但「数据已经写进库、接口却返回 500」这种，
从接口表面完全看不出来 —— 它伪装成一次普通的 500。

**对策**：Prompt 单独点名「静默失败」类缺陷，要求写清最坏后果。
这是本项目实际踩过的坑：`new_stu.stu_1d` 拼写错误导致
「学生已入库但接口报 500」，前端看到的全是失败，库里却多了一条记录。

## 四、配套的核查清单

Prompt 里第三节的核查动作，可以单独拿出来当项目体检清单用：

| # | 核查项 | 命令 / 手段 | 关注什么 |
|---|---|---|---|
| 1 | 目录结构 | 文件遍历 | 各子系统边界是否清晰 |
| 2 | 入口清单 | `main.py` / `package.json` | 启动方式是否与文档一致 |
| 3 | 路由清单 | 应用对象导出 OpenAPI | operation 数 vs 文档写的数 |
| 4 | 后端测试 | `pytest tests/ -q` | 通过/失败/报错分别归因 |
| 5 | 前端验证 | `npm run build` / `npm run verify` | 类型错误、断链 |
| 6 | 数据库基线 | 查各表行数 | 调试残留、与种子基线的偏差 |
| 7 | 环境变量 | 代码里的 `os.getenv` | 默认值、优先级、是否被 gitignore |
| 8 | 历史坑位 | 既有 README / 调试笔记 | 最容易重新踩的坑 |

## 五、这份 Prompt 的使用建议

1. **先核查再动笔。** Prompt 里核查清单排在写作要求之前，是刻意的。
   顺序反了就会先写出一个漂亮的框架，然后往里填猜测。

2. **不要跳过第 4、5 项。** 测试和构建是文档里唯一能给出
   「当前状态」的硬证据。跳过了，文档就只能描述「设计意图」，
   而接手的人需要的是「现在到底行不行」。

3. **核查中产生的中间产物要清理。** 探针数据、临时脚本、探测库，
   用完即删，并在文档里不要留下痕迹。本项目核查时曾向演示库写入
   一条探针学生（并因此触发 `stu_1d` 缺陷），核查后已删除并把
   库恢复到种子基线（200/600/134/36/12/24/12）。

4. **Prompt 是可迭代的。** 每写完一份文档，把新发现的失效模式补进第三节，
   下次就能提前规避。本文件末尾的「演进记录」就是为此保留的。
